# 2026-10-21：環境構築から Demo 0.2 まで

記録日：2026年10月21日（JST）。前段の作業は、会話で確認した内容、公開済みコミット、テスト出力から振り返って整理したものです。
リポジトリー：[godot-ai-agent-demo](https://github.com/zhanghang211202/godot-ai-agent-demo)。

## 1. まず、プロジェクト内で完結するツール環境を作った

初期プロジェクトには、Godot の標準版が使われていた。導入したい Godot-MCP は C# のエディタープラグインなので、Godot 4.7.2 の .NET 版と .NET SDK 8.0.426 が必要になった。

`godot-cli@0.31.0` は npm のローカル依存として追加し、SDK は ZIP から `.tools/dotnet/` に展開した。SDK のシステムインストーラーは使っていない。
Godot 本体の場所は利用者の指定に合わせ、起動スクリプトから `GODOT_BIN` で変更できるようにした。

ここで一度、SDK の初回実行がユーザー PATH に `.dotnet/tools` を追加した。確認後に該当する1項目だけを取り除き、起動スクリプトに `DOTNET_ADD_GLOBAL_TOOLS_TO_PATH=0` を設定した。
「ZIP を展開するだけなら、永続設定も絶対に変わらない」と思い込まないことが今回の環境構築での学びだった。

MCP はクラウドではなくループバックのローカルサーバーに接続した。接続の疎通に加えて、エディターのバージョンとプロジェクトパスを読み取るクエリーまで確認している。

## 2. 参考ゲームから、最初に残すループを絞った

題材は『Overgeared Hero / 靠装勇者』。公式紹介、利用者が指定した Wiki、YouTube の実機動画を調べた。
動画について実際に確認したのは、YouTube の storyboard から得た27枚のサンプルフレームであり、動画全体を視聴したわけではない。

抽出したループは次の通り。

> 購入 → バックパックへの配置と回転 → 合成と支援効果 → 自動戦闘 → 次の買い物

最初からペット・職業・長期育成まで入れると、このループそのものが面白いのか判断しづらい。
最初の Demo は、6×4 のバッグ、四つの商品、五回の戦闘、最後のボスに絞った。
原作のすべての合成条件や数値を再現したとは扱わず、この Demo のルールを別に定義している。

調査の詳細と参照リンクは [reference-research.md](../reference-research.md) に残した。

## 3. Demo 0.1：まず一周遊べる状態へ

初版では8種類の装備、ドラッグ配置、回転、購入・売却・更新、同種合成と短剣＋砥石の配合、自動戦闘を実装した。
一つの武器につき一つの攻撃タイマーを持ち、装備の強化を攻撃の間隔やダメージとして見せる。

![Demo 0.1 の準備画面](screenshots/v0.1/prepare.png)

![Demo 0.1 の自動戦闘](screenshots/v0.1/battle.png)

ゲームの見た目はオリジナルの森林ファンタジーにした。キャラクターと装備は、ピクセル行列とパレットをコードで作り、Godot の ImageTexture に変換している。
背景は内蔵 imagegen で作成したオリジナル画像。文字には Noto Sans CJK SC を使用し、ライセンスを同梱した。参考ゲームの元画像や音声はゲームに入れていない。

この段階で直した問題：

- 合成した瞬間、選択中のIDが消費された素材を指し続けていた。合成後の装備を選択し直すようにした。
- レシピが成立するだけで「合成可能」と表示していた。生成後の占有スペースも含めて確認するようにした。
- headless の入力テストでは、論理画面と小さなダミーウィンドウの座標系が異なった。スクリーン変換を通してマウス入力を注入した。

初版の結果は、ルール69件とUI58件、合計127件のチェック成功。
公開済みコミットは [`ac878e9`](https://github.com/zhanghang211202/godot-ai-agent-demo/commit/ac878e9653e3eeade591b97e3a1eb9ee910ddb4c)。

## 4. Demo 0.2：配置に向きと空間の判断を加えた

次の段階では、長剣を三マスにし、四つの派生装備と五つの異種合成ルートを追加した。
砥石の効果は左右の青い接続点に限定し、回転すると上下に切り替わる。画面の青い点と実際の効果判定は同じデータを使う。

![Demo 0.2 の方向付き支援マス](screenshots/v0.2/prepare.png)

![初期資源だけを使った合成例](screenshots/v0.2/forging.png)

合成例の画面は、初期の短剣2本、砥石、18ゴールドから作れる状態。撮影用にゴールドを増やしていない。
強い装備を作るとバッグ内の長さも変わるため、単に数字を上げるだけでなく、置き場所を用意する必要がある。

最初の四戦の勝利後には、三択の祝福を出すようにした。七種類の候補には、攻撃を上げる代わりに護甲を下げるもの、回復や次の買い物を助けるものがある。

![勝利後の祝福選択](screenshots/v0.2/blessings.png)

祝福を選ばずに次の波へ進むことや、同じ報酬を繰り返し受け取ることはできない。
画面右上には獲得済みの祝福を表示し、ホバーで効果を確認できる。

## 5. 続きから遊ぶためのセーブ

準備・購入・合成・報酬の選択後に自動保存し、戦闘を始める直前にも準備状態を残す。
戦闘中に終了した場合は、その戦闘の開始前から再開する仕様にした。フレーム途中の戦闘状態までは保存しない。

![一時停止・保存・読み込みのメニュー](screenshots/v0.2/menu.png)

JSON には装備のID、種類、レベル、位置、向き、ショップ、ゴールド、体力、波、祝福などを保存する。
乱数の64ビット値は、JSON の数値精度による変化を避けるため十進文字列で記録した。
読み込みはすべての項目を検証してからまとめて適用し、途中まで書き換わる状態を避ける。

最終確認では、正常に保存できること以外にも三つの問題を見つけた。

1. 壊れた旧記録がある場合、勝手に新しい旅で上書きしない。既存ファイルがあれば復帰の案内を開き、新規開始は二回の確認操作を必要にした。
2. 開戦前の保存に失敗したら、そのまま戦闘を始めない。エラー表示を残し、準備画面で再試行できるようにした。
3. 終了済みセーブの削除に失敗した場合、削除成功と表示しない。旧記録とエラー状態を確認できるようにした。

テストと撮影では、実際のプレイヤーの保存データを読み書きしない。テスト用ファイルはプロジェクト内 `.tools/test-saves/` に限定している。
